# Windows 배포판 심볼릭 링크 정리

기준: `f7e02c4` / 확인일: 2026-11-02 / 버전: 0.5.11 유지.

## 문제와 변경

[이전 설치 안내 검증](설치안내-파일-2026-11-02.md)에서 발견한 ZIP·manifest 불일치를 보완했다. macOS의 npm이 만든 `.bin` 링크를 ZIP은 링크 자체로 담지만 manifest는 대상 파일의 크기·해시를 기록하던 문제다.

- Windows PC판의 의존성 설치 직후 `cleanWindowsPayload(programDir)`를 실행한다. 중첩 `node_modules/**/.bin`을 제거하고 내부 파일·디렉터리 링크는 실제 내용으로 복사한다. 숨긴 항목도 검사한다.
- 외부 경로·끊긴 링크·순환 링크는 빌드를 중단한다. 복사하기 전에 대상 그래프를 확인하고 링크 대상의 파일 내용을 직접 복사한다. `.bin` 경로·삭제 링크·복사 링크를 빌드 로그에 남긴다.
- `writeProgramManifest`는 프로그램 루트와 모든 항목에 `lstat`를 적용한다. 파일·디렉터리·숨긴 항목·manifest 자체의 링크도 발견하면 실패한다.
- PC판 ZIP 생성 후 실제 중앙 디렉터리의 모든 항목을 확인한다. ZIP 라이브러리의 링크 속성과 Unix 파일 모드를 검사해 링크가 있으면 빌드를 실패시킨다.
- `Assert-ProgramPayload`와 설치·업데이트 스크립트는 변경하지 않았다. 비PC판의 기존 패키징 동작도 유지한다. 추가 라이브러리는 설치하지 않고 기존 archiver와 zip.js를 사용했다.

## 지운 링크와 바꾼 링크

실제 검증 빌드에서 `program/app/node_modules/.bin` 폴더 하나와 아래 링크 11개를 제거했다. 링크가 가리키는 모듈 본체는 보존했다. 표의 링크 경로는 `program/app/node_modules/.bin/` 아래이며 대상은 각 링크 기준이다.

이번 실제 패키지에서 `.bin` 밖의 남은 링크는 없어 실제 내용으로 바꾼 링크는 **0개**다. 내부 파일·디렉터리·숨긴 파일·링크가 있는 `node_modules`의 내용 복사와 중첩 `.bin` 제거는 임시 폴더 단위 테스트로 검증했다.

## EXE 없는 실제 ZIP 검증

분리된 작업 폴더에서 실행했다.

```sh
npm run release -- --target win-x64 --desktop --download-node
```

이 명령은 웹 빌드, Windows용 의존성 설치, 링크 정리, manifest 생성, ZIP 압축과 최종 링크 검사를 실행한다. `--exe`를 사용하지 않아 설치 EXE·실행기를 컴파일하지 않았다. 기존 게시 EXE·ZIP은 변경하지 않았다.

생성한 검증 ZIP을 Python zipfile로 일반 파일로 풀고, 제품의 `tests/windows-desktop/payload.test.ps1`을 macOS PowerShell 7.6.9에서 실행했다. 이 테스트는 수정하지 않은 `Assert-ProgramPayload`로 **압축 해제본 전체**를 검사한다.

| 검증 | 결과 |
|---|---|
| ZIP 항목 | 10,463개 |
| ZIP 링크 항목 | 0개 |
| 압축 해제 폴더 링크·`node_modules/**/.bin` | 모두 0개 |
| manifest 파일 | 8,722개 |
| 전체 파일 크기·SHA-256·누락·초과 검사 | Python 독립 대조와 PowerShell 제품 검사 모두 통과 |
| 패키징된 PowerShell 파일 파싱 | 5개, 오류 없음 |
| 검증 ZIP SHA-256 | `d053891108f2ad82fe24244ab54aa0f5fb3c170bd940e4e3da6dea1319e88173` |

## 링크 정리 후 서버 기동

압축 해제본의 `program/app/server/src/index.ts`를 로컬 Node 24.14.0으로 실행했다. 패키지의 `node.exe`는 실행하지 않았고 `node_modules`도 교체하지 않았다. `PATH=/usr/bin:/bin`으로 제한하고 설정·DB·백업·로그·포트(47842)를 운영 앱과 분리했다.

Windows 네이티브 OCR 모듈을 macOS에서 불러오지 않도록 제품에 원래 있는 `ECP_OCR=tesseract` 대체 경로를 선택했다. `.bin` 없이 서버가 시작됐고 `/api/health`에서 다음 응답을 확인한 뒤 검증 서버를 종료했다.

```json
{"ok":true,"application":"isumoa","protocol":1,"version":"0.5.11"}
```

이는 `.bin` 제거 후 패키지 서버 기동 확인이다. 실제 Windows 네이티브 OCR·수료증 판독·설치 EXE의 동작 검증은 아니다.

## 게시된 0.5.11 ZIP 판단과 다음 배포

기존 게시 ZIP에는 표의 링크 11개가 그대로 있다. 예를 들어 `crc32` 항목은 링크 대상 문자열 23바이트지만 manifest는 대상 실행 파일 3,919바이트의 해시를 기록한다. Windows 압축 해제기가 이를 23바이트 일반 파일로 만들면 크기·해시 검사는 실패하고, 항목을 생략해도 누락 검사에서 실패한다. 따라서 **기존 ZIP의 설치 실패 가능성은 실제 배포 결함으로 판단한다.** Windows 실기기에서 각 압축 해제 도구의 동작은 미확인이다.

**다음 공식 배포에서는 수정 코드로 Windows ZIP을 반드시 다시 만들어야 한다.** 새 ZIP과 manifest·SHA256SUMS·배포 메타데이터의 해시를 일치시켜야 한다. 이번 검증용 ZIP은 게시하지 않았으며 기존 릴리즈 파일을 교체하지 않았다.

Windows 10/11 실기기·PowerShell 5.1·탐색기/Expand-Archive의 실제 압축 해제·설치 EXE 실행은 **미확인**이다. 이번 작업에서는 버전 변경·push·EXE 빌드·릴리즈 게시를 하지 않았다. 운영 DB·원본·규칙·서명·`output/`과 기존 배포 파일을 보존했다.
